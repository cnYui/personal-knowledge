# Chat 流式失败收尾闭环设计

## 背景

当前 `main` 分支的 `chat` 页面已经接入基于 SSE 的 agentic RAG 流式对话链路，前端会消费 `timeline`、`trace`、`content`、`done`、`error` 等事件来更新 assistant 消息和思考过程。

本次排查确认的问题不是“没有进入知识图谱 agentic RAG”，而是“流式会话在失败路径上没有形成稳定闭环”。当后端异步链路中的后台任务抛错时，错误可能只出现在服务端日志中，没有稳定转换成前端可消费的 SSE `error` 事件，导致聊天界面悬挂或退化为笼统的 `network error`。

一个已经确认的真实场景是：上游模型接口返回 `502 Bad Gateway` 后，`canvas.run()` 所在的后台 producer task 抛错，但主 SSE 循环没有统一收口，前端会停在“正在理解你的问题”或仅显示不明确的网络错误。

## 问题定义

当前失败路径存在三个具体缺陷：

1. 流式异常出口不唯一。异常可能发生在 `rag_stream` 主协程，也可能发生在 `canvas.run()` 的后台任务、引用整理阶段或最终消息组装阶段，但不是所有异常都能进入同一个 SSE `error` 出口。
2. 前端收尾行为不稳定。收到结构化错误时能结束流式，但如果后端没有稳定下发 `error` 事件，前端可能一直保留 loading 状态，assistant 草稿不正常收尾。
3. 错误表达不明确。用户最后看到的可能只是笼统 `network error`，无法区分是浏览器网络层失败，还是后端已经识别出的模型上游异常。

## 目标

1. 为 `chat` 流式链路建立唯一、稳定的失败收尾路径。
2. 保证异常无论发生在主协程还是后台任务，都能被转换成一条结构化 SSE `error` 事件。
3. 保证前端在失败后结束 loading 状态，不再悬挂。
4. 保留用户问题、已展示的思考过程和已输出的正文片段，不回滚整条 assistant 消息。
5. assistant 气泡优先展示后端归一化后的结构化错误文案，而不是笼统浏览器级 `network error`。
6. 用户在失败后无需刷新页面即可立刻再次提问。

## 非目标

1. 不修改 agentic RAG 的检索策略，不讨论“是否进入知识图谱检索”。
2. 不处理上游模型 `502` 的可用性治理，不设计重试次数、退避策略、降级回答策略。
3. 不扩展为全站统一错误中心，只处理 `chat` 流式链路的失败收尾一致性。
4. 不在本次需求中重构整套聊天协议，只补齐现有协议的失败路径闭环。

## 方案对比

### 方案一：SSE 收口修复

只修复流式异常传递和前端收尾一致性。

优点：

1. 直接命中根因，范围最小。
2. 不会把本次需求膨胀成上游模型可用性治理。
3. 能在现有 `timeline/trace/content/error` 协议上完成，不要求大范围协议重构。

缺点：

1. 不解决上游 `502` 本身的频率问题。
2. 仍然依赖后端现有错误归一化质量。

### 方案二：SSE 收口 + 前端错误归一化

在方案一基础上，再统一 `chat` 页对 `ApiErrorPayload` 的展示文案。

优点：

1. 用户看到的错误文案更一致。

缺点：

1. 需求范围扩大到前端错误表达层。
2. 会模糊这次需求的核心目标，增加无关改动。

### 方案三：前端超时兜底

不深改后端，只在前端检测流超时或流提前断开后显示失败提示。

优点：

1. 改动表面较小。

缺点：

1. 这是症状修复，不是根因修复。
2. 后端异常仍然可能只停留在日志里。
3. 很难区分真实网络中断与后端业务错误。

## 选型结论

采用方案一：`SSE 收口修复`。

原因是这次需求的核心问题不是“错误如何更漂亮地展示”，也不是“如何降低上游 502 概率”，而是“失败时必须明确报错并正确结束流式会话”。只要错误出口不唯一，前端任何兜底都会变成补丁层。先把后端异常传递链路和前端收尾状态机收口，才有资格谈后续优化。

## 协议与行为设计

### 协议约束

`chat` 流式链路只允许两种合法结束方式：

1. 发送 `done`
2. 发送 `error`

不允许无声挂起。

后端必须满足：

1. 无论异常发生在 `rag_stream` 主流程、`canvas.run()` 所在后台任务、引用整理阶段还是最终消息组装阶段，都必须统一转换成一条结构化 SSE `error` 事件。
2. `error` 事件沿用现有 `ApiErrorPayload` 语义，至少包含 `message`；有能力时附带 `error_code`、`details`、`provider`、`retryable`。
3. 一旦发送 `error`，本次流式会话立刻视为结束，不再继续发送后续 `timeline`、`content` 或 `done`。
4. 后台任务异常不能只记录日志后丢失，必须显式回传到主 SSE 循环。

### 前端行为约束

前端必须满足：

1. 收到结构化 `error` 后，立即结束当前 assistant 草稿的流式状态。
2. 已显示的用户问题、`timeline`、部分正文都保留，不清空、不回滚。
3. 如果 assistant 还没有任何正文内容，则直接把错误文案写入该气泡。
4. 如果 assistant 已经有部分正文，则保留已有正文，并以失败提示作为本条消息的收尾，而不是覆盖已有内容。
5. toast 仅作为辅助提醒，不能代替消息本体中的失败结果。
6. 只有在浏览器网络层直接失败、根本没有收到后端结构化 `error` 时，才允许退回通用网络错误文案。

## 验收标准

本次需求的完成标准只看失败路径是否闭环，不看上游服务是否稳定。

必须覆盖以下场景：

1. 主流程异常。
例如 `rag_stream` 外层、引用整理阶段、消息组装阶段抛错。
预期：前端收到结构化 `error`，assistant 停止流式，错误文案写入消息区，输入框恢复可发送。

2. 后台任务异常。
例如 `canvas.run()` 放在 producer task 中执行，task 内部抛错。
预期：异常不能只停留在服务端日志，响应体里仍然能读到 SSE `error` 事件。

3. 部分输出后失败。
例如已经展示了若干 `timeline` 或部分正文后再失败。
预期：已有内容保留，消息以失败状态收尾，不回滚，不无限 loading。

4. 纯网络层失败兜底。
例如浏览器请求直接失败、连接被中断、根本没有收到后端结构化 `error`。
预期：前端仍然结束 loading，并回退到通用网络错误文案；但这属于兜底，不应覆盖正常后端错误。

## 测试边界

### 后端

需要补充流式接口测试，至少验证：

1. 主流程抛出 `ModelAPIError` 时，响应体包含 `type: error` 的 SSE 事件。
2. 后台 task 抛错时，响应体仍能包含 `type: error` 的 SSE 事件，而不是只在日志中出现 `Task exception was never retrieved`。
3. `error` 一旦输出，本次流不再继续输出 `done` 或后续正文事件。

### 前端

需要补充 `chatApi` / `useChat` 层测试，至少验证：

1. 收到 `error` 事件后，`isStreaming` 与 `assistant.isStreaming` 都会变成 `false`。
2. 已有消息列表、`timeline` 和部分正文不会丢失。
3. 当 assistant 还没有正文时，错误文案会写入 assistant 消息。
4. 当完全没有后端结构化 `error`、只有浏览器网络层失败时，仍然会退出 loading 并展示通用错误。

## 明确不接受的结果

1. 只在服务端打日志，由前端靠超时猜测失败。
2. 只弹 toast，不更新聊天消息本体。
3. 失败后 assistant 一直保持流式状态。
4. 失败后必须刷新页面才能再次发送消息。
